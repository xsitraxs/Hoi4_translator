# Аудит порта 2.0 (Rust)

Проверка версии 2.0 после слияния порта: не «компилируется ли», а «не сломает ли
она мод и не соврёт ли пользователю». Ниже — что проверялось, что нашлось, что
исправлено в этой ветке и что осталось намеренно незакрытым.

Дата: 2026-11-14. Ветка: `arena/7465385e-hoi4-translator` (от `main` = `e884e2c`).

## Метод

1. **Чтение кода** всех 15 модулей (6 419 строк) с упором на места, где ошибка
   стоит дорого: парсер `.yml`, гейт записи, кодировки, кэш, многопоточность,
   пути.
2. **Сверка с Python 1.4** из git (`6c76993`): `validation.py`, `pipeline.py`,
   `text.py`, `localisation.py`, `storage.py`, `translation.py`, `cli.py`,
   `report.py`, `config.py`, `glossary.py`, `vanilla.py` — чтобы отличить
   «регресс порта» от «так было и раньше».
3. **CI как оракул**: локального Rust-тулчейна нет, поэтому `clippy`, тесты и
   сборка под Windows выполняются в GitHub Actions; результаты читаются через
   API (логи Actions из песочницы недоступны, аннотации — доступны).
4. **Поиск «красных флагов»**: `unwrap`/`expect`/`panic!`, индексация и срезы
   строк, приведение `as`, рекурсия по файловой системе, `unsafe` (нет ни
   одного).

Что проверено по коду и подтверждено тестами: ни одного `unwrap`/`expect`/
`panic!` вне объявления статических регулярных выражений; `unsafe` не
используется; все срезы строк берутся по байтовым позициям ASCII-символов
(`"`, `\\`), поэтому паники на UTF-8 невозможны.

## Высокая серьёзность (исправлено)

### A1. Кодировки: UTF-16 портился молча, cp1252/latin-1 были недостижимы

`decode_source` пробовал UTF-8 и откатывался на cp1251. Следствия:

* объявленный набор `SOURCE_ENCODINGS` (`utf-8-sig`, `cp1251`, `cp1252`,
  `latin-1`) был мёртвым кодом: до cp1252 и latin-1 дело не доходило никогда —
  cp1251 «декодирует» почти любой байт;
* **UTF-16** файл (обычное дело после «Блокнот → Юникод») расшифровывался как
  cp1251: каждый символ превращался в правдоподобный, но чужой. Перевод шёл по
  мусору, и ни отчёт, ни лог об этом не говорили.

Исправлено: BOM UTF-16LE/BE распознаётся как объявление кодировки и файл
читается как UTF-16 (с предупреждением, что результат будет пересохранён в
UTF-8 BOM); цепочка однобайтовых кодировок повторяет кодеки Python — кандидат
отбрасывается по таблице недопустимых байтов (`0x98` для cp1251,
`0x81/0x8D/0x8F/0x90/0x9D` для cp1252), потому что WHATWG-таблицы в
`encoding_rs` отображают эти позиции в C1-контролы вместо ошибки — на этом
первая версия исправления и попалась (тест поймал до мержа).

Тесты: `every_declared_encoding_is_reachable` проверяет каждую метку из
`SOURCE_ENCODINGS`, `a_cp1251_source_is_decoded_before_it_is_translated` —
что кириллица из cp1251 доходит до перевода и выходит в UTF-8 с BOM.

Остаётся (см. B5): однобайтовый файл **не** на кириллице (немецкий или
французский мод в cp1252 без байта `0x98`) по-прежнему читается как cp1251 —
так было и в 1.4, а различить cp1251 и cp1252 без языка текста нельзя.

### A2. Файл лога не содержал сообщений конвейера

Сообщения уровня файлов (`process_file`) шли только в колбэк CLI, а в лог-файл
попадали лишь сообщения движка через `log::warn!`. В 1.4 всё писалось в
`RotatingFileHandler`, поэтому лог прогона 2.0 по упавшему файлу говорил
«ничего». Разбор жалобы «почему файл не записался» по такому логу невозможен.

Исправлено: колбэк конвейера пишет в лог-файл (новая `config::log_line`) и только
потом решает, показывать ли сообщение на консоли.

### A3. Лог рос без предела

В 1.4 был `RotatingFileHandler(maxBytes=1 МиБ, backupCount=3)`. В 2.0 — вечный
append: прогон по большому моду оставлял десятки мегабайт на диске.

Исправлено: ротация 1 МиБ × 3 бэкапа (`hoi4_translator.log.1..3`).

## Средняя серьёзность (исправлено)

### A4. `--quiet` мог скрыть ошибку записи

Фильтр был построен на префиксах текста (`"  Ошибка"`, `"  Файл"`,
`"  Превышено"`). Сообщение «  Не удалось записать файл: …» не подходило ни под
один префикс и **молча исчезало** в тихом режиме. Исправлено: фильтр по
`LogTag`, ошибки показываются всегда.

### A5. Обход папок ходил по симлинкам и джункшенам

`walk_yml` классифицировал `path.is_dir()`, а он разыменовывает ссылку. Цикл
(симлинк на родителя, типичный джункшен на Windows) — бесконечная рекурсия и
переполнение стека на ровном месте. Исправлено: `symlink_metadata` — в
симлинкованные каталоги не заходим (как `os.walk(followlinks=False)` в 1.4);
тест `symlinked_directories_are_not_walked_into`.

### A6. `pipeline.rs` — единственное место записи `.yml` — без тестов

803 строки, все решения «писать или нет» живут там, а юнит-тестов не было: только
6 интеграционных сценариев. Закрыто шестью новыми тестами, которые проходят
**без сети** (для этого у `Translator` появился тестовый шов
`with_engine_answer`, помеченный `#[doc(hidden)]`):

* строка с нечисловой версией → файл отклонён;
* ответ движка потерял `$STATE$` → файл отклонён (не записан);
* `keep-original` → записан английский текст, строка помечена восстановленной, и
  следующий прогон переводит её заново;
* движок недоступен → `error`, а не английский текст в русском файле;
* исходник в cp1251 → корректный UTF-8 с BOM;
* после записи в папке не остаётся `*.tmp`.

### A7. Совместимость кэша с 1.4 была обещанием, а не фактом

README утверждает, что ключи кэша совместимы. Ключ — sha256 от JSON-массива
`[версия, текст, src, tgt, движок]`; любое расхождение в сериализации (экранирование,
порядок, `ensure_ascii`) делает всю базу 1.4 бесполезной. Добавлен
known-answer-тест: хэши посчитаны алгоритмом Python и зафиксированы в
`cache.rs` (`cache_keys_stay_compatible_with_the_python_build`), в том числе на
строке с кириллицей.

## Средняя серьёзность (осталось)

### A8. На Windows замена файла не атомарна

`fs::rename` не перезаписывает существующий файл на Windows, поэтому код делает
`remove_file` + `rename`. Есть окно, когда файла нет (не «полуфайла» — именно
отсутствие). Игра в этот момент может не увидеть строку, но не упадёт. Честная
замена — `ReplaceFileW`/`MoveFileEx(MOVEFILE_REPLACE_EXISTING)` через `windows-sys`;
это новый крейт, поэтому решение отложено до релиза/GUI, а документация
исправлена (раньше комментарий обещал «старое или новое содержимое» без оговорки).

### A9. «Осиротевшие» `.tmp` не убираются

Если процесс убили в момент записи, рядом останется `.<имя>.<pid>.<n>.tmp`.
Игра такие файлы игнорирует, но папка мусорится. Предложение: при старте удалять
`*.tmp` старше суток в целевом каталоге. Не сделано: удаление чужих файлов —
решение, которое стоит принимать явно, а не молча.

### A10. Два потока вывода

Конвейер пишет в stdout, `log::*` движков — в stderr. В лог-файл теперь попадает
всё (A2), но на консоли это два потока. Оставлено осознанно: stdout — «что
делаем с файлами», stderr — диагностика движков; при перенаправлении вывода это
разделение удобно. В GUI оба потока нужно будет завернуть в один канал.

## Сверка с 1.4 — что совпало

Проверено построчно и подтверждено тестами:

* набор флагов CLI (`--src/--dst/--target/--source-lang/--engine/--api-key/--java-jar/--glossary/--vanilla/--concurrency/--skip-translated/--broken-lines/--no-report/--dry-run/--quiet/--cli/--version`), коды возврата 0/1/2;
* схема SQLite: таблицы `cache` и `file_sources` с теми же колонками и индексом; ключ `file_sources` — абсолютный путь с `normcase` (`os.path.normcase(os.path.abspath(...))` ↔ `path_key`);
* политика записи: битые строки исходника → пишем как есть и сообщаем; битые строки перевода → отказ от файла либо `keep-original`; дубли и неформатные строки → отказ;
* порядок кодировок и предупреждение о пересохранении в UTF-8 BOM;
* размер запроса 400 символов, защита маркеров `<<PHn>>`, типографика по языку, разделитель CSV `;`.

## Что это значит для GUI

Аудит закрывает риски, которые в GUI стали бы дороже (кодировки, лог, гейт
записи). Перед Tauri 2 остаётся:

1. **Вынести прогон из библиотеки в отменяемую задачу.** `process_file` уже
   принимает `&AtomicBool stop` и колбэк прогресса, но список файлов обходится
   циклом внутри `cli::run` — нужна структура `Job`, которую GUI сможет
   запустить в фоне, слушать прогресс и останавливать.
2. **Один канал сообщений.** Сейчас консоль и лог расходятся (A10): в GUI нужен
   один поток событий (`file started/finished`, `line progress`, `warning`).
3. **Настройки.** `config::settings_file()` пока не используется — GUI сохранит
   туда последние папки, движок, ключ (лучше в keyring, как в 1.4).
4. **Предпросмотр.** В 1.4 был диалог предпросмотра переводов; в 2.0 остался
   только `--dry-run` (структурная проверка). Нужен явный выбор: делать
   постраничный предпросмотр или обойтись отчётом.
5. **Прогресс по строкам.** `line_progress` уже есть в `translate_batch`, но
   `cli` передаёт `None`; GUI будет первым реальным потребителем.

## Как воспроизвести

```bash
cargo test --all                      # 93 теста, без сети
cargo clippy --all-targets
cargo fmt --all --check
cargo run -- --src examples/demo-mod --dst /tmp/out --target ru --dry-run
```

CI прогоняет это на каждый pull request, плюс `cargo build --release` и
smoke-тест `.exe` на тегах. Логи Actions читаются через аннотации прогона —
в них попадают упавшие тесты и остаток работ по `rustfmt`.
